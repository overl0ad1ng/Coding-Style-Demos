**会产生错误业务结果的问题**

1. **[P1] 批量提现共享全局状态，会把一个商家的钱转到另一个商家的账户。**
   位置：[09-payout-session.ts:34](./09-payout-session.ts:34)，相关状态定义在第 4 行。

   `tenantId`、`accountId`、`grossCents`、`feeCents` 是模块级变量。`payMerchant()` 写入这些变量后，会在 `await loadAdjustment()` 暂停；与此同时，`payMerchants()` 用 `Promise.all()` 启动另一个商家，覆盖这些变量。维护者必须跨多个 setter 和异步恢复点，推导哪些数据还属于同一个商家。

   **运行复现：**同时处理 A、B 两个商家，最终两笔转账的租户和银行账户都成了 B。
   **建议：**让商家信息、调整金额、手续费在单次调用内保持为局部数据，组装完整的 `Transfer` 后传给银行。批量并发本身符合需求，可以保留。

2. **[P1] 日报预览覆盖了租户过滤，会把其他租户的金额算进来。**
   位置：[14-report-screen.ts:18](./14-report-screen.ts:18)，调用顺序见第 32 行。

   `installTenant()` 给 `report.select` 包装了租户过滤，随后 `installPreview()` 又把同名处理器替换成 `rows => rows`。预览本应只放宽“已结算”条件，却同时取消了租户限制。理解这个问题需要追踪注册、装饰、覆盖的先后顺序。

   **运行复现：**A 租户已结算 100 分、未结算 200 分，B 租户 900 分；A 的预览应为 **300 分**，实际返回 **1200 分**，结果还标着 `tenantId: 'A'`。
   **建议：**把租户过滤设为固定步骤，让 `preview` 只控制结算条件。结合 [13-report-runtime.ts:1](./13-report-runtime.ts:1)，当前字符串注册表、`any` 和动态装饰机制也没有 README 所述的扩展需求支撑，直接使用有类型的函数流程更容易检查。

3. **[P1] 非幂等扣款复用了自动重试，而且把“结果未知”当成“没付成功”。**
   位置：[04-payment-gateway.ts:25](./04-payment-gateway.ts:25)，重试逻辑在第 5 行。

   `retryRequest()` 对异常和 5xx 最多重试三次，查询状态和扣款都使用它。但 README 明确说扣款接口不保证幂等：服务端可能已经扣款，只是响应丢失。之后 `catch` 又抹掉错误，把结果变成 `paid: false`，上层进一步返回 `'try-again'`。

   **运行复现：**模拟每次已处理扣款但响应丢失，一次 `payOrder()` 发出了 **3 次扣款请求**，最终仍提示重试。
   **建议：**保留读取操作的重试能力；扣款需要明确的幂等保证或状态核对流程。返回契约应能区分成功、明确失败和结果未知，避免未知结果引导再次付款。

4. **[P1] 退款政策有统一入口，但接口、邮件和管理列表各自重写，已经产生规则分歧。**
   位置：[12-refund-actions.ts:9](./12-refund-actions.ts:9)、[邮件判断:17](./12-refund-actions.ts:17)、[管理列表:23](./12-refund-actions.ts:23)。

   `requestRefund()` 和管理列表漏了“尚未发货”；邮件使用 `< 168` 小时，统一政策则允许恰好到截止时间。维护者要同时核对天、小时、毫秒三种表达，才能判断它们是否一致。

   **运行复现：**已发货订单的按钮不可退款，接口却实际创建了退款；恰好第 7 天时，按钮允许退款，邮件隐藏退款链接。
   **建议：**这些入口统一调用已有的 [canRefund / refundAmount](./11-refund-policy.ts:19)。这里已有合适的政策所有者，无须再新建一套判断。

5. **[P1] 购物车预览、提交和收据各维护一份配送规则，金额已经不一致。**
   位置：[03-cart-pricing.ts:3](./03-cart-pricing.ts:3)、[提交计算:10](./03-cart-pricing.ts:10)、[收据计算:19](./03-cart-pricing.ts:19)。

   预览按商品原价判断 `>= 10000`；提交按折后金额判断；收据又用了原价 `> 10000`。变量名不同，但它们维护的是同一项业务政策，维护者必须逐项对照才能发现差异。

   **运行复现：**会员商品原价合计 10000 分、普通配送时，预览为 **9000 分**，提交和收据却都是 **9800 分**。
   **建议：**建立一个明确负责商品折扣和配送费的计算入口，让三个场景复用结果。另外，[01-order-processing.ts:58](./01-order-processing.ts:58) 为非 CN 地址设置了 2500 分配送费，也与 README 给出的普通配送 800 分规则冲突，应一并核对和收敛。

6. **[P1] 提现手续费计算早于金额调整，即使单个商家执行也会算错。**
   位置：[09-payout-session.ts:37](./09-payout-session.ts:37)。

   先按原金额计算手续费，再载入调整额修改总额，却没有重新计算手续费。这要求调用者记住几个独立操作的隐含顺序。

   **运行复现：**原金额 10000 分，调整增加 1000 分，实际转出 **10800 分**；按调整后总额收取 2%，应转出 **10780 分**。
   **建议：**先得到调整后总额，再在同一个局部计算中推导手续费和转账金额，避免维护可失效的派生状态。

7. **[P1] 客户导出没有等待保存结束，保存失败也会显示“导出成功”。**
   位置：[06-customer-export.ts:45](./06-customer-export.ts:45)，失败处理见第 34 行。

   `forEach(async ...)` 不会等待回调里的 Promise，因此立刻执行 `finishExport()` 并返回 `{ ok: true }`。同时，`saveCustomer()` 捕获异常后返回 `null`，调用方完全忽略结果。维护者必须穿过多个函数才能发现，“完成”“成功”“保存完成”实际上没有关联。

   **运行复现：**保存 Promise 仍未完成时，导出已返回 `{ ok: true, saved: 0 }`，状态为 `done: true`；模拟保存失败，按钮仍返回“导出成功”。
   **建议：**显式等待全部保存操作，并统一选择抛错或汇总失败结果的契约；成功应在确认所有客户保存完成后产生。

8. **[P1] 导出取消只改变标记，执行流程不响应；新任务还会继承旧状态。**
   位置：[06-customer-export.ts:13](./06-customer-export.ts:13)、[cancelExport:24](./06-customer-export.ts:24)。

   没有保存流程读取 `cancelled`，`beginExport()` 也不清理 `cancelled`、`failed` 和 `error`。多个布尔字段可以同时表示完成、失败、取消，维护者需要自己解释这些组合到底意味着什么。

   **运行复现：**取消后保存仍完成，`saved` 继续增加；下一次失败后出现 `done: true、failed: true、cancelled: true` 的组合。
   **建议：**使用明确的任务状态和每次运行独立的上下文，在保存之间检查取消信号；如果底层支持中止，再向其传递信号。每次启动应初始化本次任务状态。

9. **[P1] 账户设置把回调接口当作可等待操作，数据库失败也提前返回“已保存”。**
   位置：[07-customer-accounts.ts:38](./07-customer-accounts.ts:38)。

   **运行复现：**让 `repository.find()` 拒绝，调用方得到的仍是 **“已保存”**。
   **建议：**按 README 已明确的迁移方向，把更新接口统一为 Promise，让调用方等待查找和保存完成，再返回结果。

10. **[P1] 展示物流页面会预留库存，而且卡片和浮层各触发一次。**
